# Spovishun Kotlin Architecture Rules (project override)

Project-specific concretions layered on top of the generic `kotlin-style.md` rule
(installed from spovishun-skills). Where the generic rule says "a `Result`-like wrapper"
or "via DI", Spovishun mandates the specific types below. This file is a Spovishun-owned
override — it is NOT generated by spovishun-skills and must survive re-installs.

## ResultContainer (the project's Result type)
- The "Result-like wrapper" in `kotlin-style.md` is `ResultContainer` — own sealed class:
  `Success<T>(val data: T)` / `Failure(val exception: BaseException)`. NOT Kotlin's `Result`.
- Services and repository interfaces return `ResultContainer`. Nullable returns in the domain
  layer are forbidden — use `ResultContainer` instead.
- Chain with `.flatMap {}`, resolve with `.fold(onSuccess = {}, onFailure = {})`.
- Business errors: `sealed class` or `ResultContainer.Failure` — never exceptions.

## Exposed ORM
- ALL database access MUST run inside an Exposed transaction — opened by `safeDbQuery {}`, never by
  a `transaction {}` / `newSuspendedTransaction {}` call of your own.
- `safeDbQuery {}` (in `data/db/DatabaseFactory.kt`) is the ONLY entry point — it already does
  `withContext(Dispatchers.IO)` + `transaction {}` + `ResultContainer.catching`. Never assemble
  those by hand. `safeDbTransaction` was deleted in spovishun-173: it skipped the `Dispatchers.IO`
  hop and ran blocking JDBC on the caller's dispatcher.
- No class hardcodes `Dispatchers.IO`. It is named in exactly two places, both infrastructure:
  `DatabaseFactory.kt`, and the `BlockingTelegramDispatcher`-qualified binding in
  `:app` `di/ConfigModule.kt` (blocking Telegram HTTP calls must not sit on the CPU-sized
  `Dispatchers.Default` pool). Adding a third requires the same justification in DI, not in a class.

## Koin DI
- The "via DI" in `kotlin-style.md` is Koin. `single {}` for services/repositories/long-lived
  objects; `factory {}` for use cases and short-lived objects.
- Declare bindings with the constructor DSL — `singleOf(::PingController)`, and
  `singleOf(::StartCommand) bind BotCommand::class` when a secondary type is needed. It resolves the
  constructor itself, so the module file stops tracking arity — adding a parameter needs no DI edit,
  and no one has to count `get()` calls against a constructor to read a binding (spovishun-176).
  This is a legibility and churn change, not a safety one: `get()` is reified and already infers each
  parameter's type. A chain of `get()` is allowed only where `singleOf` cannot express the
  resolution — a parameter qualifier (`get(named<ReadinessScope>())`), a `getAll()` collection, or a
  factory call rather than a constructor — and such a binding carries a one-line comment saying which.
- Constructor injection only — no `by inject()` inside business logic classes. The single exception is
  the composition root, `:app` `Application.kt` (`object Application : KoinComponent`): it is an
  `object` with no constructor to inject into, and it is what starts Koin. Nothing in `:domain`,
  `:data`, `:bot` or `:admin-api` may use `by inject()` or implement `KoinComponent`.
- Bind by interface: `single<MemberRepository> { MemberRepositoryImpl() }`. This outranks the
  constructor DSL for repositories — `singleOf(::MemberRepositoryImpl) bind MemberRepository::class`
  would make the concrete impl the primary type and therefore resolvable, which is what the rule
  exists to prevent.
- Inject `CoroutineDispatcher` / `CoroutineScope` via Koin — never hardcode `Dispatchers.IO`.
- Every injected `CoroutineScope` MUST carry a scope-level `CoroutineExceptionHandler` in its
  context (`SupervisorJob() + dispatcher + exceptionHandler + CoroutineName(...)`). A `SupervisorJob`
  alone only isolates sibling failures; without a handler an uncaught throw reaches the JVM default
  handler and is silently swallowed. For schedulers/background scopes use `SchedulerExceptionHandler`.
- When two bindings share a type (e.g. multiple `CoroutineScope`s), distinguish them with a typed
  qualifier (`named<Marker>()`) — never a stringly-typed `named("...")`.

## Enforced thresholds (detekt) — spovishun-169

`kotlin-style.md` states review targets. `config/detekt/detekt.yml` states the ceiling CI enforces.
The two are deliberately different numbers, and the gap is the point: a target you aim for, a ceiling
that fails the build. Before spovishun-169 only the target existed, and nothing checked it.

| Concern | Target (`kotlin-style.md`) | Enforced ceiling | detekt rule |
|---|---|---|---|
| Function length | ~20 lines | **30** lines of code | `LongMethod` |
| Function parameters | max 3 | **4** | `LongParameterList` |
| Constructor parameters | max 3 | **4** (data classes exempt) | `LongParameterList` |
| Nesting depth | ≤ 2 | **4** | `NestedBlockDepth` |
| Returns per function | guard clauses encouraged | **4** | `ReturnCount` |

Exceeding a target is a review conversation; exceeding a ceiling is a build failure. Nesting is the
one row where the gap is wide and knowingly unclosed — tightening `NestedBlockDepth` to 2 was not in
spovishun-169's scope.

**detekt runs with type resolution.** The rules above, plus `InjectDispatcher` (no hardcoded
`Dispatchers.*`), `UnsafeCallOnNullableType` (no `!!`) and `SleepInsteadOfDelay` (no `Thread.sleep`
in tests), require a compile classpath — see the Linting section of the root `CLAUDE.md` for how the
`detekt` task is wired and why it must not be simplified back.

Never hand-edit `.claude/rules/kotlin/kotlin-style.md` to record project numbers: it is a
plugin-managed artifact (`kind: rule`, `id: kotlin/kotlin-style` in `spovishun-skills.lock.yaml`) and
an edit is both reported as drift by `doctor` and overwritten by the next `spovishun-skills sync`.
Project-specific numbers belong in this file.

## Import aliasing (Telegram Bot type clash)
- When an external type clashes with a project class, use `import as` consistently across the module:
  ```kotlin
  import com.github.kotlintelegrambot.Bot as TelegramBot
  ```
